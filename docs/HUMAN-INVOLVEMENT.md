# 人工参与核查 · 2026-10-23

依据：当前代码与本次用户纠正。这里说明真实实现，不把开发测试覆盖不足转成用户的业务审批工作。本轮只纠正照片审核职责并盘点其余人工点，不擅自删除尚待产品方确认的流程。

## 已纠正：照片由 ListingAgent 自动审核

卖家上传正面、俯视、侧面照片并提交 → ListingAgent 校验表单、调用校园模型检查方向、描述一致性、清晰度和相关性 → PricingAgent / SupervisionAgent 完成后续图步骤 → 自动返回 published 或 rejected。没有人工审核队列、人工批准按钮或“组员看照片后放行”条件。

不通过：拒绝上架，卖家按错误提示修改并重提。模型不可用：拒绝上架并提示稍后重提，也不转人工。演示照片显式走 demo 路径；它不代表真实模型审核。自动化证据包括真实重复角度负例；尚未建立真实正例准确率基准，只是测试覆盖限制，不是需要用户完成的人工照片验收任务。

证据：backend/app/agents.py 的 specialist('ListingAgent')、supervision；backend/app/main.py 的 action / ensure_media；backend/app/domain.py 的 save_listing。

## 现有人工参与点

| H05 | 买家订单已收货 | 买家点击确认完好收货 | 同一事务自动完成交易、解除留置、结算并写账本 | 正常收货操作；当前必须买家确认，没有倒计时自动验收，也不需管理员再结算 |

| H09 | 程序停止、VPN断开或部署时 | 操作者启动 Docker/VPN；开发者运行部署脚本或提供有效配置 | 服务启动、连接数据库和校园模型 | 环境维护，不是订单人工流程。当前没有业务登录功能 |

## 两处需要产品方核对的具体实现

**H06 交付问题解除**：frontend/src/Buyer.jsx 暴露提交问题入口；frontend/src/ui.jsx 的 Demo 暴露 resolve 按钮；backend/app/domain.py 的 advance('issue'/'resolve') 设置/清除 issue，advance('confirm') 会因 issue 阻止结算。界面文字“按政策解决”不等于当前有自动证据裁决；现在依靠手动模拟解除。

**H07 政策缺口决策**：frontend/src/Manager.jsx 的 Exceptions 页面；backend/app/agents.py 的 supervision / human_review；backend/app/domain.py 的 policy_decision。管理员界面目前只有一个固定处理方向，必填自由文本是理由；系统生成的是预设受约束政策，不是从任意文本自主编写新规则。有现行政策时 conflict 自动记录处理并清除承运接受标记，仍须再次模拟承运确认。

“物业拒绝通行”也仍是可选回复，拒绝后不能承运确认；当前没有改回复入口。若 MVP 的“不考虑异常”也包括物业拒绝，H03 的这个分支同样需要明确是否保留。

## 自动执行、无需额外人工审批的部分

照片审核与上架结论、偏好解析与前三推荐、配送尺寸/前置条件校验、固定金额 breakdown、模拟订单创建、物业回复同步、用户侧 Agent 名称隐藏、买家确认后的即时结算、管理统计，以及管理方向提交后的政策生效，均无需另找人工批准。

本轮不新增任何业务页面规则提示，避免把内部审核盘点展示给最终用户。仅更新交付与架构说明。既有源码包作为历史版本保留，新包包含本次纠正。
